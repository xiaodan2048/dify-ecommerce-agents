# 电商售后 Agent 迷你复刻版 · Dify 搭建指南

> 零代码基础可以照做：所有代码都已经写好，你只需要**复制粘贴**，并按本文把变量名一个个对上。
> 品牌（清屿、元养）、买家、订单全部是虚构的。演示环境的"现在"固定为 **2026-10-26 14:00**，所以每次测试结果都一样。

预计用时：第一次搭大约 6–8 小时，可以分两个周末完成。

> **本指南已按 Dify 里实际搭好的「售后Agent-演示」同步（2026-10-28 核对）**：Agent 用 2 个工具（query_order、after_sales），所有模型节点都是 **deepseek-v4-flash**。早期拆成 3 个工具的代码放在 `dify代码节点/旧版_三个工具时/`，只留作参考，不要再用。

## 0. 你会做出什么

```
买家发消息
   │
[A 会话预处理] 代码：提取订单号；判断是不是在回复「确认 / 算了」
   │
[B 条件分支]
   ├─ 确认修改 ──→ [C 执行改地址] → 清空待确认 → 回复
   ├─ 取消修改 ──→ 清空待确认 → 回复"已取消"
   └─ 其他 ──→ [D 保存订单号] → [E 问题分类器]
                    ├─ 物流与发货 → [F 物流与发货] 代码（固定流程）     → 回复
                    ├─ 修改地址   → [G 提取新地址] → [H 改地址校验] 代码 → 回复"请确认"
                    ├─ 退换货     → [I 售后Agent] 自己决定调哪个工具 → [J 越权检测] → 回复
                    ├─ 投诉与人工 → [K 转人工] 代码                      → 回复
                    └─ 其他       → [L 兜底回复] LLM → [M 越权检测2]    → 回复

I 售后Agent 能用的 2 个工具（各自是一个"工作流"，发布成工具）：
  query_order   查订单（只读；只能查到当前买家在本店的订单）
  after_sales   售后办理，用 action 区分：
                  action=check_policy   按品牌政策判定能不能退（只读；规则写在代码里，模型不能改结论）
                  action=create_ticket  建工单（写操作；转人工可直接建，补发等必须买家确认）
```

核心设计一句话：**能画出流程图的走固定流程，只有退换货判定这种条件多、品牌差异大的场景交给 Agent。**

## 1. 准备工作（约 30 分钟）

1. 打开 https://cloud.dify.ai 注册登录。右上角头像 → 语言，切成「简体中文」。
2. **准备一个支持 Function Calling 的模型**。推荐 DeepSeek（便宜，国内能直接充值）：
   - 去 https://platform.deepseek.com 注册，充值 10 元，创建一个 API Key 并复制下来。
   - 回到 Dify：左侧「集成」→「模型供应商」→ 找到深度求索（DeepSeek）→ 安装 → 填 API Key → 保存。所有模型节点选 **deepseek-v4-flash**。
   - 用通义千问也可以，安装「通义千问」插件，填阿里云百炼的 Key。
3. **安装 Agent 策略插件**：顶部「插件」→「探索 Marketplace」→ 搜 `Agent`，安装 langgenius 官方的 **Dify Agent Strategies**（里面带 FunctionCalling 和 ReAct 两种策略）。
4. 把本文件夹解压到桌面，方便随时打开 `dify代码节点/` 里的文件复制。
   Mac 上用「文本编辑」打开 .py 文件，打开后按 `Cmd + A` 全选，再按 `Cmd + C` 复制。

## 2. 第一步：做 2 个工具（约 1 小时）

每个工具都是一个独立的「工作流」应用，结构都一样：**开始 → 代码执行 → 结束**，最后「发布为工具」。

### 通用操作（两个工具都按这个流程走）

1. 「工作室」→「创建空白应用」→ 选 **工作流**（不是 Chatflow）→ 填名字 → 创建。
2. 点「开始」节点 → 右侧「输入字段」点 `+` → 字段类型选「文本」，**变量名称**按下表填（一个字都不能错），勾选「必填」。不用必填的字段会单独注明。
3. 鼠标移到开始节点右侧的 `+` → 添加「代码执行」节点：
   - 语言选 **Python3**。
   - 「输入变量」：按下表逐个添加。左边填变量名，右边点选「开始」里同名的变量。
   - 代码框：先全选删掉原有代码，再粘贴对应 .py 文件的全部内容。
   - 「输出变量」：添加 `result`，类型 `String`。
4. 在代码节点后面添加「结束」节点 → 输出变量：名字填 `result`，值选「代码执行 / result」。
5. 右上角「运行」，随便填一组测试值（例如 order_id=`QY20261025001`、buyer_id=`U1001`、shop=`清屿官方旗舰店`），能看到返回的一段 JSON 就说明成功了。
6. 右上角「发布」→「发布更新」，然后在发布菜单里点 **「发布为工具」**：
   - 工具调用名称：按下表填英文名。
   - 工具描述、每个参数的描述：按下表**原样复制**。模型就是靠这些描述来判断什么时候调用、参数怎么填。
   - 保存。

> 以后改了工作流，要再点一次「发布」，工具才会更新。

### 工具 1：query_order

| 项目 | 内容 |
|---|---|
| 应用名 | 工具-查订单 |
| 开始节点字段 | `order_id`、`buyer_id`、`shop` |
| 代码文件 | `dify代码节点/工具1_query_order.py` |
| 工具调用名称 | `query_order` |
| 工具描述 | 按订单号查询本店订单的状态、商品、金额、物流和售后情况。只能查到当前买家在本店的订单。 |
| 参数描述 | order_id：订单号，以 QY 或 YY 开头 ／ buyer_id：必须使用系统提供的当前买家ID ／ shop：必须使用系统提供的当前店铺名 |

### 工具 2：after_sales（售后办理）

| 项目 | 内容 |
|---|---|
| 应用名 | 工具-售后办理 |
| 开始节点字段 | `action`、`order_id`、`buyer_id`、`shop`、`reason_type`、`opened`、`ticket_type`、`summary`、`buyer_confirmed`（只有 action、buyer_id、shop 勾必填） |
| 代码文件 | `dify代码节点/工具2_after_sales.py` |
| 工具调用名称 | `after_sales` |
| 工具描述 | 售后办理工具，用 action 选择操作。action=check_policy：按品牌售后政策判定订单能否退换货（只读），返回结论 decision（可办理/不可办理/需补充信息/需转人工/已在售后中/订单未找到）、依据条款、所需凭证、运费承担和下一步，必须按返回结论回复买家。action=create_ticket：创建售后工单（写操作），转人工可以直接创建；补发、质量问题审核等其他类型必须先向买家复述并得到买家明确同意后才能调用。 |
| 参数描述 | action：操作类型，只能是 check_policy（判定能否退换货）或 create_ticket（建工单） ／ order_id：订单号，以 QY 或 YY 开头；转人工且没有订单号时可留空 ／ buyer_id：必须使用系统提供的当前买家ID ／ shop：必须使用系统提供的当前店铺名 ／ reason_type：check_policy 时填：退货原因，只能是 无理由、质量问题、物流破损、少件错发 之一，不确定就留空 ／ opened：check_policy 时填：是否拆封，只能是 未拆封、已拆封、未知 ／ ticket_type：create_ticket 时填：只能是 转人工、补发、质量问题审核、物流异常、催发货 ／ summary：create_ticket 时填：一句话概括买家诉求 ／ buyer_confirmed：create_ticket 时填：买家已明确同意时传 是，否则留空 |

**为什么判定和建工单合成一个工具**：两者共用同一份订单数据和售后政策，合在一个工作流里只维护一份代码；读和写靠 action 区分，写操作在代码里还要校验 buyer_confirmed，模型漏传就办不成。

**自测**：action 填 `create_ticket`、ticket_type 填「补发」、不填 buyer_confirmed，应该返回 `NEED_BUYER_CONFIRM`。这就是"写操作必须先确认"在起作用。再试 action 填 `check_policy`、order_id=`QY20261012008`、buyer_id=`U1004`、shop=`清屿官方旗舰店`、reason_type=`无理由`、opened=`未拆封`，应返回「可办理」，rule_id 是 `QY-R1P`（大促延长）。

## 3. 第二步：搭主流程（约 3 小时）

「工作室」→「创建空白应用」→ 选 **Chatflow** → 名字填「售后Agent-演示」。
新建后画布上默认有「开始 → LLM → 直接回复」三个节点，**先把 LLM 和直接回复删掉**。

### 3.1 会话变量和开始节点

1. 画布右上角找到「会话变量」（图标像 `{x}`）→ 添加 3 个，类型都选 `String`，默认值留空：
   `current_order_id`、`pending_action`、`urged_orders`
   这三个变量就是 Agent 的"会话记忆"：记住订单号、记住等待确认的修改、记住催过的订单。
2. 点「开始」节点 → 输入字段 `+` → 添加 2 个**下拉选项**字段：
   - `buyer_id`：选项依次填 U1001 到 U1010（共 10 个）
   - `shop`：选项填 `清屿官方旗舰店`、`元养官方旗舰店`
   真实业务里买家身份由系统自动带入，这里用下拉框模拟。

### 3.2 逐个添加节点

下表的「从哪连过来」指的是上游节点。**每个节点的标题都改成表里的名字**，比如「A 会话预处理」，后面选变量时好找。

| 节点 | 类型 | 从哪连过来 | 配置 |
|---|---|---|---|
| **A 会话预处理** | 代码执行 | 开始 | 粘贴 `节点A_会话预处理.py`。输入：`query`←sys.query，`current_order_id`←会话变量，`pending_action`←会话变量。输出：`order_id` String，`route` String |
| **B 是否在确认改地址** | 条件分支 | A | IF：`A/route` 是 `confirm`；点「+ ELIF」：`A/route` 是 `cancel`；剩下的走 ELSE |
| **C 执行改地址** | 代码执行 | B 的 IF | 粘贴 `节点C_执行改地址.py`。输入：`pending_action`←会话变量，`buyer_id`←开始，`shop`←开始。输出：`answer` String |
| C2 清空待确认 | 变量赋值 | C | 会话变量 `pending_action`，操作选「清空」 |
| C3 回复 | 直接回复 | C2 | 内容：插入 `C 执行改地址/answer` |
| X1 清空待确认 | 变量赋值 | B 的 ELIF | 会话变量 `pending_action` → 清空 |
| X2 回复 | 直接回复 | X1 | 直接写文字：`好的，已取消修改，地址保持不变～` |
| **D 保存会话状态** | 变量赋值 | B 的 ELSE | 第一行：`current_order_id` 覆盖为 `A/order_id`；点 `+` 加第二行：`pending_action` 清空 |
| **E 问题分类器** | 问题分类器 | D | 输入变量 sys.query；模型选 deepseek-v4-flash；5 个分类和指令照抄 `提示词/E_问题分类器.md`；打开「记忆」，窗口 6 |
| **F 物流与发货** | 代码执行 | E 的分类 1 | 粘贴 `节点F_物流与发货.py`。输入：`query`←sys.query，`order_id`←A/order_id，`buyer_id`、`shop`←开始，`urged_orders`←会话变量。输出：`answer` String，`urged_orders` String |
| F2 记录已催 | 变量赋值 | F | `urged_orders` 覆盖为 `F/urged_orders` |
| F3 回复 | 直接回复 | F2 | 插入 `F/answer` |
| **G 提取新地址** | 参数提取器 | E 的分类 2 | 按 `提示词/G_参数提取器.md` 配置 |
| **H 改地址校验** | 代码执行 | G | 粘贴 `节点H_改地址校验.py`。输入：`order_id`←A/order_id，`buyer_id`、`shop`←开始，`new_address`←G/new_address。输出：`answer` String，`pending_action` String |
| H2 记录待确认 | 变量赋值 | H | `pending_action` 覆盖为 `H/pending_action` |
| H3 回复 | 直接回复 | H2 | 插入 `H/answer` |
| **I 售后Agent** | Agent | E 的分类 3 | 见下面 3.3 |
| **J 越权检测** | 代码执行 | I | 粘贴 `节点J_越权检测.py`。输入：`text`←I/text，`order_id`←A/order_id。输出：`answer`、`hit`、`hit_words`，都是 String |
| J2 回复 | 直接回复 | J | 插入 `J/answer` |
| **K 转人工** | 代码执行 | E 的分类 4 | 粘贴 `节点K_转人工.py`。输入：`query`←sys.query，`order_id`←A/order_id，`buyer_id`、`shop`←开始。输出：`answer` String |
| K2 回复 | 直接回复 | K | 插入 `K/answer` |
| **L 兜底回复** | LLM | E 的分类 5 | 模型 deepseek-v4-flash；SYSTEM 粘贴 `提示词/L_兜底回复_系统提示词.md`（把【插入变量】换成真的变量）；USER 插入 sys.query；打开记忆，窗口 4 |
| **M 越权检测2** | 代码执行 | L | 和 J **完全一样的代码**，只是输入 `text` 改成 ←L/text |
| M2 回复 | 直接回复 | M | 插入 `M/answer` |

> **代码节点最容易出错的地方**：输入、输出变量的名字和类型必须和 .py 文件顶部注释里写的一模一样。每个文件开头都列好了，照着填就行。

### 3.3 I 售后Agent 节点

| 配置项 | 填什么 |
|---|---|
| Agent 策略 | FunctionCalling（模型不支持函数调用时换成 ReAct） |
| 模型 | deepseek-v4-flash |
| 工具 | 点「添加」→「工作流」页签 → 勾选 query_order、after_sales；每个参数都保持「自动」 |
| 指令 | 粘贴 `提示词/I_售后Agent_指令.md` 中注释以下的全部内容。遇到【插入变量：xxx】时，删掉这几个字，在原位置输入 `/` 选对应变量 |
| 查询（Query） | sys.query |
| 记忆 | 打开，窗口 10 |
| 最大迭代次数 | 5 |

为什么 buyer_id 写在指令里，而不是让买家自己说：工具会校验"订单号 + 买家ID + 店铺"三者是否匹配，查不到别人的订单。真实系统里身份由服务端注入，模型根本拿不到；这里用指令模拟。

### 3.4 跑通检查

右上角「预览」→ 选 buyer_id=`U1004`、shop=`清屿官方旗舰店` → 发 `QY20261012008 没拆封，不想要了能退吗`。
回复里应该说可以退，并提到大促延长到 15 天（这单签收 12 天，按普通 7 天规则是不能退的）。点回复下方的日志/追踪图标，展开 I 售后Agent，能看到依次调用了 query_order 和 after_sales（action=check_policy）。

## 4. 第三步：跑评测（约 2 小时）

打开 `评测/评测集_v1.2_1027.xlsx`（50 条用例），「说明」页写了标注口径。流程：

1. 每条用例先在预览里**重新开始对话**，按表选好买家ID和店铺。
2. 逐句发「买家输入」，对照「期望结果要点」和「红线」，在黄色列填 1/0。
3. 「工具调用正确」只看走 Agent 的用例：在日志里看它调了哪些工具、reason_type 和 opened 填得对不对。
4. 失败的用例在「失败原因」下拉里选一个原因。「汇总」页会自动算出任务完成率、工具调用正确率、越权率，以及失败原因分布。
5. 改一处提示词，就把 50 条全部重跑一遍，把两次汇总截图放在一起，这就是"回归"。

第一次跑不到 75% 很正常。失败原因分布就是迭代方向：看哪类错最多、改什么、改完提升了多少。

## 6. 常见问题

| 现象 | 原因和解决办法 |
|---|---|
| 代码节点报 `Output xxx is missing` 或类型错误 | 输出变量名或类型和代码不一致，对照文件顶部注释改 |
| 代码节点报 `name 'xxx' is not defined` | 代码没有复制全。重新 `Cmd + A` 全选文件再粘贴 |
| Agent 不调用工具，直接自己回答 | ① 模型不支持函数调用，换 deepseek-v4-flash 或策略换 ReAct ② 工具描述没填，回到工具应用补上描述并重新发布 |
| Agent 说"没查到订单"，但订单号是对的 | 预览里选的买家ID或店铺和用例不一致；或者指令里的【插入变量】没有换成真的变量 |
| 买家说"拆了"被分到「其他」 | 问题分类器没开记忆，或者分类 3 的描述没复制全 |
| 上一条用例的订单号被带到下一条 | 没有重新开始对话。会话变量会记住订单号，这本身就是"多轮记忆"功能 |
| 改完地址再查，显示的还是旧地址 | 正常。演示数据写在代码里，"修改成功"只是模拟，不会真的写入数据 |
| 想换成今天的真实日期 | 不建议。日期固定，评测结果才稳定；要换的话，需要所有用例的期望结果一起重算 |

## 7. 设计取舍 Q&A

- **为什么规则不直接写进提示词，让模型判断？**
  因为签收天数、大促窗口、金额阈值这类判断，模型会算错，而且结果不可复现。用代码判，结论稳定、可审计；政策改了只改数据，不用重新调提示词。
- **为什么 J 越权检测用正则，而不是再加一个模型？**
  成本低、零延迟、命中原因看得见。缺点是会误杀和漏检，所以用评测集里的红线用例来校准。真实业务里会再叠一个小模型做语义判断。
- **你的评测集怎么保证有代表性？**
  按 5 类意图 × 简单/多轮/边界分层，边界用例专门覆盖越权诱导、提示词注入、跨店铺订单、超额度退款、冷链特殊政策。
- **这个 demo 和真实系统差在哪？**
  身份由服务端注入、真实订单接口、并发和超时重试、人工坐席系统对接、线上监控。
