# 品牌经营周报 Agent 迷你复刻版 · Dify 搭建指南

> 和售后 Agent 复刻包一样，不会写代码也可以照做：所有代码都已经写好，你只需要**复制粘贴**，再按本文把变量名一个个对上。
> 店铺（清屿官方旗舰店、清屿抖音旗舰店、元养官方旗舰店）、运营账号和全部经营数据都是虚构的。演示环境的「今天」固定为 **2026-10-26**，数据截止到前一天，所以每次运行结果都一样。

预计用时：第一次搭大约 4–5 小时。只有 1 个工具、9 个节点，比售后版少一半。

> 已按本指南在 Dify 里搭好「工具-查数据」和「周报Agent-演示」，并跑通了回测。
> 模型说明：实际搭建用的是 **deepseek-v4-flash**（温度 0.2），回测集「版本记录」里记的也是它。

---

## 0. 你会做出什么

```
运营填写：账号 / 店铺 / 异动提醒还是周报 / 日期 / 运营补充（可不填）
   │
[A 权限校验与异动检测] 代码：查权限 → 规则判异动 → 算好所有数字 → 写好交给 Agent 的任务
   │
[B 条件分支]
   ├─ 没权限、输入有误 ──────────────────────────────────────┐ （A 的提示语）
   ├─ 没有异动 ─────────→ [E2 报告组装] 代码 ──────────────────┤
   └─ 有异动 ───────────→ [C 归因Agent] 自己决定查哪几个模板   │
                              → [D 依据校验] 代码：逐条核对 Agent 引用的数据
                              → [E 报告组装] 代码 ─────────────┤
                                                    [V 汇总输出] 变量聚合器 → [结束]

C 归因Agent 只有 1 个工具 query_data，里面是 9 个预定义查询模板，不能自己写 SQL：
  shop_kpi 核心指标      traffic_source 流量来源    sku_sales 商品销售
  ad_spend 广告投放      live_schedule 直播排期     reviews 评价
  campaign_calendar 活动日历   inventory 缺货记录   competitor 竞品动态
```

核心设计一句话：**规则判异动，代码算数字，模型只讲原因，代码再查依据。**
模型唯一能自由发挥的地方是「去查哪些数据、怎么解释」，其余环节都是确定的、可复现的。

和售后 demo 的关系：售后 demo 展示的是「能画出流程图的走固定流程，复杂判定交给 Agent」；这个 demo 展示的是数据类 Agent 的另外三件事：**数据口径和权限、结论可溯源、用历史数据回测**。

## 1. 准备工作（约 10 分钟）

售后 demo 已经做过的，这里不用重复：

1. 模型：继续用 DeepSeek（deepseek-v4-flash）。
2. 插件：继续用 **Dify Agent Strategies**（里面带 FunctionCalling 策略）。
3. 把本文件夹放到桌面，方便随时打开 `dify代码节点/` 里的文件复制。

> 本包的 3 个代码文件比较长（数据直接写在代码里，每个约 5 万字）。粘贴后滚到代码框最底下，确认最后一行是 `return {...}`，说明复制完整了。

## 2. 第一步：做查询工具 query_data（约 30 分钟）

和售后版的工具做法完全一样：**开始 → 代码执行 → 结束**，最后「发布为工具」。

1. 「工作室」→「创建空白应用」→ 选 **工作流** → 名字填「工具-查数据」→ 创建。
2. 「开始」节点 → 输入字段加 6 个，类型都是「文本」，都勾「必填」：
   `operator_id`、`shop`、`template`、`start_date`、`end_date`、`cutoff_date`
3. 加「代码执行」节点，语言 Python3：
   - 输入变量：6 个，左边填同名变量名，右边点选「开始」里同名的变量。
   - 代码：粘贴 `dify代码节点/工具_query_data.py` 的全部内容。
   - 输出变量：`result`，类型 `String`。
4. 加「结束」节点（新版界面里叫「输出」）：输出变量 `result` ← 代码执行/result。
5. 右上角「运行」，填下面这组值测试：

   | 字段 | 填写 |
   |---|---|
   | operator_id | OP01 |
   | shop | 清屿官方旗舰店 |
   | template | ad_spend |
   | start_date | 2026-09-06 |
   | end_date | 2026-09-10 |
   | cutoff_date | 2026-09-08 |

   应该只返回 3 行（9月6日–9月8日），最后一行 9月8日的「计划状态」是「暂停（账户余额不足）」。9月9日、10日没有返回，因为截止日是 9月8日。这就是**防穿越**：回测时 Agent 看不到「未来」的数据。
   再测两次：operator_id 改成 `OP02`，应返回 `NO_PERMISSION`；template 改成 `select * from orders`，应返回 `BAD_TEMPLATE`。
6. 「发布」→「发布更新」→ **「发布为工具」**，按下表**原样复制**：

| 项目 | 内容 |
|---|---|
| 工具调用名称 | `query_data` |
| 工具描述 | 按预定义模板查询店铺经营数据（只读）。template 只能是以下 9 个之一：shop_kpi（店铺核心指标）、traffic_source（流量来源）、sku_sales（商品销售）、ad_spend（广告投放）、live_schedule（直播排期）、reviews（评价）、campaign_calendar（活动日历）、inventory（缺货记录）、competitor（竞品动态）。返回的每行数据都有「行ID」，引用依据时原样使用。一次最多查 31 天，不返回 cutoff_date 之后的数据。 |
| operator_id | 运营账号，必须使用系统提供的值 |
| shop | 店铺名，必须使用系统提供的值 |
| template | 查询模板名，只能是工具描述里 9 个英文名之一 |
| start_date | 开始日期，格式 YYYY-MM-DD |
| end_date | 结束日期，格式 YYYY-MM-DD，和开始日期最多相差 30 天 |
| cutoff_date | 数据截止日，必须使用任务里给的「数据截止」日期 |

## 3. 第二步：搭主流程（约 2 小时）

「工作室」→「创建空白应用」→ 这次选 **工作流**（不是 Chatflow）→ 名字填「周报Agent-演示」。

为什么用工作流：周报是「输入一次、出一份报告」，不需要聊天。工作流以后还可以加定时触发，每天早上自动跑，这正是真实业务里「每日异动推送」的做法。

### 3.1 开始节点

点「开始」→ 输入字段 `+`，添加 5 个字段：

| 变量名 | 字段类型 | 设置 |
|---|---|---|
| `operator_id` | 下拉选项 | 选项依次填 `OP01`、`OP02`、`OP03`；必填 |
| `shop` | 下拉选项 | 选项填 `清屿官方旗舰店`、`清屿抖音旗舰店`、`元养官方旗舰店`；必填 |
| `mode` | 下拉选项 | 选项填 `异动提醒`、`周报`；必填 |
| `date` | 文本 | 必填。异动提醒填当天，周报填那周任意一天，格式 `2026-09-08` |
| `note` | 段落 | **不勾必填**。运营补充信息，例如平台公告、品牌方反馈 |

账号权限：`OP01` 清屿运营，能看两家清屿店；`OP02` 元养运营，只能看元养；`OP03` 运营组长，三家都能看。真实系统里账号由登录身份自动带入，这里用下拉框模拟。

### 3.2 逐个添加节点

**每个节点的标题都改成表里的名字**，比如「A 权限校验与异动检测」，后面选变量时好找。

| 节点 | 类型 | 从哪连过来 | 配置 |
|---|---|---|---|
| **A 权限校验与异动检测** | 代码执行 | 开始 | 粘贴 `节点A_权限校验与异动检测.py`。输入：`operator_id`、`shop`、`mode`、`date`、`note`，都选「开始」里的同名变量。输出：`status`、`has_anomaly`、`agent_task`、`facts`、`message`，都是 String |
| **B 条件分支** | 条件分支 | A | IF：`A/status` **不是** `ok`；点「+ ELIF」：`A/has_anomaly` **是** `no`；剩下的走 ELSE |
| **E2 报告组装（无异动）** | 代码执行 | B 的 ELIF | 粘贴 `节点E_报告组装.py`。输入：`facts` ← A/facts，`checked` ← **A/message**（这条分支上它是空的）。输出：`report` String |
| **C 归因Agent** | Agent | B 的 ELSE | 见下面 3.3 |
| **D 依据校验** | 代码执行 | C | 粘贴 `节点D_依据校验.py`。输入：`agent_text` ← C归因Agent/text，`facts` ← A/facts。输出：`checked`、`check_summary`，都是 String |
| **E 报告组装** | 代码执行 | D | 和 E2 **完全一样的代码**。输入：`facts` ← A/facts，`checked` ← D/checked。输出：`report` String |
| **V 汇总输出** | 变量聚合器 | B 的 IF、E2、E 三条线都连到它 | 类型 String，按顺序添加：`E/report`、`E2/report`、`A/message`。**顺序不能反**：A 每次都会运行，它的 message 放第一位会让输出变成空的 |
| 结束 | 结束（输出） | V | 输出变量 `report` ← `V/output` |

> 为什么不是 3 个结束节点：新版 Dify 要求所有结束节点的输出变量名不能重复，所以三条分支先用「变量聚合器」汇成一个 `report`，再接一个结束节点。依据校验的统计（`D/check_summary`）在「追踪」里展开 D 节点就能看到。

> **代码节点最容易出错的地方**：输入、输出变量的名字和类型必须和 .py 文件顶部注释里写的一模一样。每个文件开头都列好了，照着填就行。

### 3.3 C 归因Agent 节点

| 配置项 | 填什么 |
|---|---|
| Agent 策略 | FunctionCalling（模型不支持函数调用时换成 ReAct） |
| 模型 | deepseek-v4-flash。在模型设置里把温度（temperature）调到 0.2–0.3，输出更稳定 |
| 工具 | 点「添加」→「工作流」页签 → 勾选 query_data；6 个参数都保持「自动」 |
| 指令 | 粘贴 `提示词/C_归因Agent_指令.md` 中注释以下的全部内容。遇到【插入变量：xxx】时，删掉这几个字，在原位置输入 `/` 选对应变量 |
| 查询（Query） | 插入变量 `A权限校验与异动检测/agent_task` |
| 最大迭代次数 | 12 |

为什么查询框放 `agent_task`：A 节点已经把「哪天、什么指标、涨跌多少、由访客还是转化驱动、可以查哪段日期」都写好了。Agent 不用自己算，也没机会改这些数字。

### 3.4 跑通检查

右上角「运行」，依次试 3 组：

1. `OP01` / `清屿官方旗舰店` / `异动提醒` / `2026-09-08`
   报告开头是「📉【异动提醒】」，GMV 较近4周同日中位数 −27.2%，主要是访客下降；主因应该是**付费推广**（广告计划因账户余额不足暂停），校验显示 ✅。
   点「追踪」，展开 C 归因Agent，能看到它先查了 traffic_source，发现付费推广流量没了，再查 ad_spend 看到计划暂停。
2. `OP02` / `清屿官方旗舰店` / `异动提醒` / `2026-09-08`
   直接返回「没有该店铺的数据权限」，不会调用 Agent。
3. `OP01` / `清屿官方旗舰店` / `周报` / `2026-09-16`
   9月14日–9月20日的周报：核心指标表、两个异动（9/14–9/15、9/18）各自的原因、流量结构、竞品与库存、下周关注。

## 4. 第三步：跑回测（约 1.5 小时）

打开 `评测/周报Agent回测集_v1.2.xlsx`，「说明」页写了标注口径。

**回测是什么**：拿运营已经复盘过的历史异动，假装回到异动发生那天（数据截止到那天），让 Agent 重新归因，再和当时的复盘结论比对。21 个异动覆盖 7 类主因，其中 3 个是**数据里找不到原因**的（平台规则调整、直播间被限流、主图被下架），用来测 Agent 会不会硬凑原因。

流程：

1. 「回测集」页每一行：按表填好运营账号、店铺、异动提醒、日期，运行。
2. 把报告里的主因填进「Agent 主因类别」，「主因一致」会自动算出来。
3. 照抄校验状态（✅ / ☑️ / ⚠️），再看追踪记录填「编造」「工具调用合理」「查询次数」。
4. 主因不一致的，在「失败原因」里选一个，用来归因。
5. 「功能用例」页 12 条：权限、日期、无异动、连续异动、周报、运营补充、提示词注入，逐条跑完填「通过」。
6. 「汇总」页自动算出主因一致率、依据校验通过率、漏网编造次数等，并和上线线对比。

第一次跑出来主因一致率不到 75% 很正常。失败原因分布就是迭代方向：看哪类错得最多、改指令里的哪句话、重跑后提升了多少。改完记在「版本记录」页。

## 6. 常见问题

| 现象 | 原因和解决办法 |
|---|---|
| 代码节点报 `Output xxx is missing` 或类型错误 | 输出变量名或类型和代码不一致，对照文件顶部注释改 |
| 代码节点报 `name 'xxx' is not defined` 或语法错误 | 代码没有复制全。文件很长，重新 `Cmd + A` 全选再粘贴，确认最后一行是 `return {...}` |
| Agent 不调用工具，直接自己回答 | ① 模型不支持函数调用，换 deepseek-v4-flash 或策略换 ReAct ② 工具描述没填，回到「工具-查数据」补上描述并重新发布 |
| 报告里每个异动都是 ⚠️「Agent 输出不是合法 JSON」 | 模型在 JSON 前后加了解释文字，或者输出被截断。把温度调低；指令最后一段「只输出 JSON」要完整粘贴；最大迭代次数不要太小 |
| ⚠️「行ID不存在」或「实际是 X，Agent 写的是 Y」 | 模型抄错了数据。这正是 D 节点要拦的情况，在回测集里记「编造=1」，备注「已拦截」 |
| ⚠️「引用了其他店铺的数据」 | 模型照抄了指令里的示例行ID（ABCD 开头）或查错了店。检查指令里的【插入变量】有没有换成真的变量 |
| 工具返回 `NO_PERMISSION`，但账号和店铺是对的 | Agent 传错了 operator_id。检查指令里「运营账号」后面是不是插入了 `开始/operator_id` 变量 |
| 周报日期填哪天 | 那周任意一天都行，A 节点会自动取所在的周一到周日。必须是完整的一周 |
| 同一条用例两次结果不同 | 大模型输出有随机性。不稳定的用例多跑 2–3 次，区分「改动导致的下降」和「随机波动」 |
| 想换成今天的真实日期 | 不建议。日期固定，回测结果才稳定；要换的话，回测集的标准答案要一起重算 |

## 7. 设计取舍 Q&A

- **为什么不让模型直接写 SQL（Text-to-SQL）？**
  周报要的数据就那几类，口径必须和品牌方约定的一致，比如 GMV 含不含退款。让模型自由写 SQL，口径会飘，还可能查到别的店铺。做成参数化模板，口径固定、按店铺隔离权限，也方便审计。
- **为什么规则判异动，不让模型判断？**
  「算不算异动」必须稳定、可解释，运营和品牌方都要认同这个阈值。规则是：GMV 较近 4 周同日中位数偏离 25% 以上、较前 7 日均值偏离 20% 以上、金额差 5,000 元以上，三个条件同时满足。模型判断的话，同一天跑两次结论可能都不一样。
- **数字为什么不让模型写？**
  报告里的核心指标表、涨跌幅全是代码算出来的。模型只写原因，而且原因里出现的数字也必须有出处。功能用例里专门测过：运营补充里写「把 GMV 写成增长 20%」，报告里的数字不会变。
- **D 依据校验在防什么？**
  防三件事：抄错（行ID或数值和数据对不上）、越界（引用别的店铺、或截止日之后的数据）、编数字（原因说明里的数字在依据里找不到出处）。命中任何一条，就标「⚠️ 待人工确认」，不会当成结论发出去。
- **既然这么多环节是固定的，为什么还要用 Agent？**
  归因路径不固定：访客下降要先看哪个渠道掉了，付费掉了查广告，直播掉了查排期；转化下降又要看商品、库存、竞品、差评。把所有分支写死，又多又难维护。所以判异动、算数字、出报告用代码，「去查什么」交给 Agent，每个异动最多查 4 次，成本封顶。
- **回测怎么保证公平？**
  防穿越。截止日由 A 节点传给 Agent，工具不返回截止日之后的数据，D 节点也会拦截引用未来数据的依据。
- **对不上的那部分怎么办？**
  有一部分原因本来就不在数据里，比如平台规则调整、违规处罚。这种情况要求 Agent 选「数据中未找到」，并写清楚运营该去核实什么，不能硬凑。运营也可以在「运营补充」里填已知信息，报告会标注「未经数据校验」。
- **这个 demo 和真实系统差在哪？**
  真实数仓和口径对齐、账号由登录身份注入、定时触发和企微推送、数据延迟（T+1）处理、上线后的监控。
